# CatchTheSun: демонстрация Calculation Engine через Swagger

Сценарий создаёт один демонстрационный участок, четыре варианта, четыре критерия и 16 значений. Затем запускает AHP, TOPSIS и Pareto на одной матрице и показывает детали, результаты и историю.

Все данные ниже учебные. Это не результаты UrbanSketch и не нормативное заключение.

Для изолированной PostgreSQL БД и безопасного запуска приложения сначала выполните [инструкцию по demo-окружению](demo-environment.md).

## Перед запуском

Используйте отдельную демонстрационную БД с применёнными миграциями. Не направляйте сценарий на production или на основную рабочую БД. API читает `ConnectionStrings:DefaultConnection`; сейчас `appsettings.json` указывает на БД `catchthesun`, поэтому для изолированной демонстрации переопределите строку подключения через User Secrets или переменную окружения.

Swagger UI доступен в Development по адресу `/swagger` на URL запущенного API. Откройте его и выполняйте запросы ниже в указанном порядке.

В модели `Criterion` нет связи с `Site`: критерии глобальные. `CalculationService` требует включить **все активные `IsRequired=true` критерии** в каждый расчёт. Для сценария используйте чистую демонстрационную БД без других таких критериев. Если в БД уже есть активные обязательные критерии, их тоже нужно добавить в расчёты и заполнить для всех вариантов.

Создайте демонстрационные критерии с `IsRequired=false`, чтобы они не стали обязательными для других расчётов. Все четыре критерия всё равно будут явно включены в каждый запрос.

## 1. Участок

`POST /api/sites`

```json
{
  "name": "DEMO26 — жилой квартал у парка",
  "location": "Екатеринбург, демонстрационная площадка",
  "area": 24000
}
```

Сохраните `id` из ответа как `siteId`. Поле `Site.Area` в Entity не содержит единицу измерения; для этого примера принято соглашение, что значение задаётся в м². Это допущение должно совпадать с тем, как проект интерпретирует площадь участка.

## 2. Варианты

Для каждого запроса используйте `POST /api/sites/{siteId}/variants`, подставляя `siteId` из ответа на предыдущем шаге.

**A — максимум жилой площади, высокая стоимость**

```json
{
  "name": "DEMO26-A — высокая жилая площадь",
  "externalId": "DEMO26-A"
}
```

**B — экономичный вариант**

```json
{
  "name": "DEMO26-B — экономичный",
  "externalId": "DEMO26-B"
}
```

**C — приоритет инсоляции**

```json
{
  "name": "DEMO26-C — солнечный",
  "externalId": "DEMO26-C"
}
```

**D — сбалансированный вариант**

```json
{
  "name": "DEMO26-D — сбалансированный",
  "externalId": "DEMO26-D"
}
```

Сохраните четыре `id` вариантов как `variantAId` … `variantDId`.

## 3. Критерии

Создайте каждый критерий через `POST /api/criteria`. В текущем API `CriterionDirection` сериализуется числом: `0 = Maximize`, `1 = Minimize`, `2 = Target`. Swagger покажет enum; выбирайте указанный вариант.

**Жилая площадь — Maximize, м²**

```json
{
  "name": "DEMO26 — жилая площадь",
  "description": "Общая площадь жилых помещений",
  "unit": "м²",
  "direction": 0,
  "isRequired": false,
  "isActive": true
}
```

**Стоимость строительства — Minimize, млрд ₽**

```json
{
  "name": "DEMO26 — стоимость строительства",
  "description": "Оценочная стоимость строительства для учебного примера",
  "unit": "млрд ₽",
  "direction": 1,
  "isRequired": false,
  "isActive": true
}
```

**Продолжительность инсоляции — Maximize, ч/сутки**

```json
{
  "name": "DEMO26 — продолжительность инсоляции",
  "description": "Условная средняя длительность прямой инсоляции жилых помещений",
  "unit": "ч/сутки",
  "direction": 0,
  "isRequired": false,
  "isActive": true
}
```

**Плотность застройки — Target, коэффициент FAR**

```json
{
  "name": "DEMO26 — плотность застройки",
  "description": "FAR = общая площадь надземных этажей / площадь участка; цель 1.55",
  "unit": "м²/м² (FAR)",
  "direction": 2,
  "targetValue": 1.55,
  "isRequired": false,
  "isActive": true
}
```

Цель FAR 1.55 соответствует примерно 37 200 м² общей площади этажей на участке 24 000 м². Сохраните IDs критериев как `livingId`, `costId`, `sunId`, `farId`.

## 4. Матрица значений

Используйте `POST /api/variants/{variantId}/criteria-values`. Для каждой ячейки таблицы отправьте отдельный запрос с соответствующими `variantId` и `criterionId`:

```json
{
  "criterionId": "{{criterionId}}",
  "value": 25500
}
```

Замените `{{criterionId}}` реальным GUID критерия. Значения матрицы:

| Вариант | Жилая площадь, м² | Стоимость, млрд ₽ | Инсоляция, ч/сутки | FAR |
|---|---:|---:|---:|---:|
| A — высокая площадь | 25 500 | 3.60 | 2.8 | 1.85 |
| B — экономичный | 20 800 | 2.55 | 2.7 | 1.35 |
| C — солнечный | 21 800 | 3.18 | 3.8 | 1.50 |
| D — сбалансированный | 22 600 | 3.05 | 3.4 | 1.55 |

Отправьте все 16 значений ровно по одному разу. Для наглядной физической проверки примера подразумеваются общие площади этажей A/B/C/D около 44 400/32 400/36 000/37 200 м² и пятна застройки около 7 400/6 000/6 000/6 200 м². Пятна застройки меньше участка, жилая площадь меньше общей площади этажей. Эти проверочные площади не являются отдельными полями API и не отправляются.

## 5. AHP + Weighted Sum

`POST /api/calculations`. В этом API веса AHP выводятся из сравнений, поэтому `weight` для критериев не задавайте. Отправьте все шесть пар. В `CriterionAId` указывается более приоритетный критерий, `Value` — сила предпочтения по Saaty.

Значения `[2, 4, 4, 2, 2, 1]` соответствуют согласованному вектору приоритетов `[4, 2, 1, 1]`; обратные элементы матрицы сервис достраивает сам. Все значения входят в шкалу Saaty, а CR для такой матрицы равен 0 (с допуском численной реализации).

```json
{
  "siteId": "{{siteId}}",
  "variantIds": ["{{variantAId}}", "{{variantBId}}", "{{variantCId}}", "{{variantDId}}"],
  "method": "AHP",
  "criteria": [
    { "criterionId": "{{livingId}}" },
    { "criterionId": "{{costId}}" },
    { "criterionId": "{{sunId}}" },
    { "criterionId": "{{farId}}" }
  ],
  "comparisons": [
    { "criterionAId": "{{livingId}}", "criterionBId": "{{costId}}", "value": 2 },
    { "criterionAId": "{{livingId}}", "criterionBId": "{{sunId}}", "value": 4 },
    { "criterionAId": "{{livingId}}", "criterionBId": "{{farId}}", "value": 4 },
    { "criterionAId": "{{costId}}", "criterionBId": "{{sunId}}", "value": 2 },
    { "criterionAId": "{{costId}}", "criterionBId": "{{farId}}", "value": 2 },
    { "criterionAId": "{{sunId}}", "criterionBId": "{{farId}}", "value": 1 }
  ]
}
```

Ожидаемые ориентиры: HTTP `201`, `ConsistencyRatio` около 0 и сохранённые веса около 0.5, 0.25, 0.125, 0.125.

## 6. TOPSIS

`POST /api/calculations`. Веса должны быть заданы для каждого критерия, лежать в `[0,1]` и суммироваться в 1 с допуском `0.000001`. Для сопоставимости используются те же веса, что и ожидаемый вектор AHP. Попарные сравнения для TOPSIS не передаются.

```json
{
  "siteId": "{{siteId}}",
  "variantIds": ["{{variantAId}}", "{{variantBId}}", "{{variantCId}}", "{{variantDId}}"],
  "method": "TOPSIS",
  "criteria": [
    { "criterionId": "{{livingId}}", "weight": 0.5 },
    { "criterionId": "{{costId}}", "weight": 0.25 },
    { "criterionId": "{{sunId}}", "weight": 0.125 },
    { "criterionId": "{{farId}}", "weight": 0.125 }
  ],
  "comparisons": []
}
```

## 7. Pareto

Для демонстрации Pareto-фронтов запрос не передаёт веса. Они для Pareto необязательны; без них `Score` и `ParetoSecondaryScore` остаются `null`. Попарных сравнений нет.

```json
{
  "siteId": "{{siteId}}",
  "variantIds": ["{{variantAId}}", "{{variantBId}}", "{{variantCId}}", "{{variantDId}}"],
  "method": "Pareto",
  "criteria": [
    { "criterionId": "{{livingId}}" },
    { "criterionId": "{{costId}}" },
    { "criterionId": "{{sunId}}" },
    { "criterionId": "{{farId}}" }
  ],
  "comparisons": []
}
```

В этой матрице у каждого варианта есть компромисс по критериям, поэтому ожидается, что все четыре будут недоминируемыми и окажутся на Pareto Front 1. Это полезная проверка: `Rank` у них может совпадать и не заменяет `ParetoFront`.

## 8. Показ истории и сохранённых snapshots

Каждый успешный POST должен вернуть `201 Created`, ID расчёта и `Location` на его детали. После каждого POST выполните:

- `GET /api/calculations/{id}` — проверьте метод, критерии, веса (где они используются), AHP-сравнения, диагностику и четыре результата с snapshots входных значений;
- `GET /api/calculations/{id}/results` — покажите Score/Rank/Pareto-поля и значения, зафиксированные для каждого варианта;
- после трёх POST вызовите `GET /api/sites/{siteId}/calculations` — должно быть три записи истории, у каждой `resultCount = 4`.

Для AHP/TOPSIS ожидаются числовые `Score` и `Rank`; Pareto без весов возвращает `Score: null`, `ParetoSecondaryScore: null`, а `ParetoFront` и `Rank` — заполненными.

## Повторный запуск

Критерии глобальны и уникальны по имени, а API не предоставляет endpoint удаления расчётов. Поэтому повторяйте весь сценарий в новой отдельной демонстрационной БД, либо меняйте префикс `DEMO26` на новый уникальный и создавайте новый участок/варианты. Не удаляйте таблицы и не сбрасывайте рабочую БД для повторной демонстрации.
